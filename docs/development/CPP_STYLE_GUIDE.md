# Стиль C++ в GlamDB

Правила для собственного кода GlamDB на C++23: публичных заголовков, ядра,
приложений, тестов и probes. Сторонние зависимости и сгенерированный код не
переформатируются и не переименовываются.

Этот документ задаёт стиль; [`.clang-format`](../../.clang-format) должен
реализовывать его механические правила. При изменении правил обновляйте
конфигурацию и проверки вместе с кодом. Форматтер не заменяет проверку имён,
порядка объявлений, владения и обработки ошибок. Не обходите расхождение правил
и конфигурации массовыми `clang-format off` или подавлением диагностик.
Команды проверок описаны в [BUILDING](BUILDING.md#quality).

Стиль не меняет контрактов [архитектуры](../ARCHITECTURE.md): ошибки ввода,
I/O и исчерпания ресурсов остаются сообщаемыми результатами; успешный статус
не заменяет доказательства долговечности данных.

## Общие правила

Сохраняйте стиль окружающего кода, если он не противоречит этим правилам.
Если примеров нет, выбирайте наиболее распространённый в проекте вариант.

Старайтесь укладывать тело функции в один экран, примерно до сорока строк.
Это ориентир для выделения самостоятельных операций, а не повод создавать
обёртки без собственной ответственности.

Комментарии, описания изменений и PR должны быть краткими: оставляйте только
необходимый контекст. Косметические изменения и рефакторинг, не связанные
с задачей, выносите в отдельный PR.

### Отступы и пустые строки

Используйте четыре пробела и строки до 120 символов. Каждый уровень продолжения
выражения получает один дополнительный отступ.

Разделяйте пустой строкой логически независимые части кода, группы полей
и инклюдов. Не оставляйте две пустые строки подряд или пустую строку перед
закрывающей скобкой блока.

Перед `public:`, `protected:` и `private:` нужна пустая строка, кроме случая,
когда секция начинается сразу после открывающей скобки типа.

## Именование

| Сущность | Правило | Примеры |
| --- | --- | --- |
| Классы, структуры и псевдонимы типов | `CamelCase` с префиксом `T` | `TStoreDirs`, `TOptions`, `TFileHandle` |
| Интерфейсы | `CamelCase` с префиксом `I` | `ILocalFs`, `IListener` |
| Перечисления | `CamelCase` с префиксом `E` | `EFileState`, `EFileKind` |
| Неймспейсы | `CamelCase` с префиксом `N` | `NGlamDB`, `NIO`, `NStorage` |
| Функции и методы | `CamelCase` | `ComputeSize`, `GetState` |
| Локальные переменные и параметры | `camelCase` | `fileSize`, `attemptID` |
| Локальные `static` и `thread_local` переменные | `CamelCase` | `CurrentContext` |
| Приватные и защищённые поля | `CamelCase` с суффиксом `_` | `Latch_`, `StoredLength_` |
| Публичные поля, константы и значения enum | `CamelCase` | `Length`, `MaxFileSize`, `DirSynced` |
| Макросы | `UPPER_SNAKE_CASE` | `GLAMDB_CORE_IO_RESULT_INL_H_` |

Имена полей внешних форматов и сгенерированных интерфейсов сохраняют их контракт,
например `snapshot_id` и `record_count`. Для значения с самостоятельным смыслом
объявляйте псевдоним через `using`, если он делает интерфейс понятнее.

У итераторов используйте суффикс `It`: `fileIt`, `recordIt`. Короткое `it`
допустимо, когда в контексте естественно есть только один итератор.

Имена функций начинаются с глагола: `CountFiles`, а не `FilesCount`.
Для получения сохранённого значения используйте `Get`; для нетривиального
вычисления — `Compute`, `Calculate` или другой точный глагол.
Имена обработчиков обратного вызова начинаются с `On`.
Булевы запросы называют проверяемое свойство: `IsOpen`, `HasError`, `CanRead`.

### Семантика имён и ошибок

- `CheckIdentity` и `CheckSchema` возвращают ошибку или результат проверки.
- `ValidateSchema` бросает исключение при некорректном вводе. Если интерфейс
  ядра должен возвращать статус, называйте такую проверку `CheckSchema`;
  не меняйте её протокол ошибок ради имени.
- `FindFile` и `TryGetFile` допускают отсутствие результата. Отсутствие объекта
  и ошибка чтения должны различаться.
- `GetState` возвращает сохранённое значение, а `GetFile` предполагает наличие
  объекта как инвариант вызывающего кода. Пользовательское отсутствие объекта,
  ошибка I/O и повреждение данных требуют проверки и сообщаемого результата;
  они не должны попадать в путь аварийного завершения.
- Суффикс `OrThrow` допустим только там, где исключения являются явным
  контрактом интерфейса. Он не заменяет обработку ошибок в ядре.

Не переименовывайте методы внешнего интерфейса при `override`: Arrow, Iceberg,
GoogleTest и стандартные протоколы сохраняют заданные ими имена и сигнатуры.
Это также относится к `main`, операторам и методам для стандартной совместимости,
например `begin` и `end`. Исключение не распространяется на собственные методы,
которые можно назвать по правилам проекта.

### Аббревиатуры и английский язык

Аббревиатуры из двух букв пишутся заглавными (`IO`, `ID`), из трёх и более —
как обычные слова (`Cpu`, `Gpu`, `Uuid`, `Json`). В логах и текстах ошибок
используйте обычное написание аббревиатур: `IO`, `CPU`, `UUID`, `JSON`.

Для одной величины используйте единственное число: `fileCount`, а не
`filesCount`. Для исчисляемых величин используйте `count`, для неисчисляемых —
`amount`.

Проверяйте множественное число английских терминов: `media`, `indices` или
`indexes`, `criteria`. В английских комментариях и документации числа меньше
десяти пишите словами, кроме конкретных значений и литералов кода.

## Неймспейсы

Внутри неймспейса отступы не используются. Комментарий после закрывающей скобки
точно повторяет открытое имя; для анонимного неймспейса пишите `// namespace`.
Для визуального разделения допустима отбивка из восьмидесяти символов `/`,
но добавлять её механически в короткие файлы не нужно.

```cpp
namespace NGlamDB::NIO {

void Process()
{ }

} // namespace NGlamDB::NIO

namespace {

void Helper()
{ }

} // namespace
```

Не указывайте лишний квалификатор уже открытого неймспейса. Внутри `NGlamDB::NIO`
используйте `TFileStat`, а не `NGlamDB::NIO::TFileStat`.

## Заголовочные файлы

Подключайте заголовки группами, разделёнными пустой строкой:

1. Локальные файлы. В `.cpp` первым идёт соответствующий ему `.h`.
2. Остальные заголовки GlamDB, сгруппированные по папкам.
3. Сторонние библиотеки через их публичные пути подключения.
4. Стандартная библиотека C++ и системные заголовки.

Внутри группы сортируйте полные пути по алфавиту. Группы папок проекта тоже
сортируются по пути. Соответствующий `.cpp` заголовок остаётся первым независимо
от сортировки. Не включайте приватные файлы зависимости из её исходного дерева
вместо установленного публичного интерфейса.

Собственный публичный заголовок должен быть самодостаточным и компилироваться
без приватных заголовков, HTTP/Python-зависимостей и случайных транзитивных
инклюдов. В обычных `.h` используйте `#pragma once`.

## Классы, структуры и интерфейсы

Для пассивных наборов публичных данных используйте `struct`. Если появляются
приватные поля или методы, используйте `class` и явную секцию `public:`.

Секции располагаются в порядке `public`, `protected`, `private`. В каждой
секции сначала объявляются поля, затем методы. Связанные поля группируются
вместе и отделяются от других групп пустой строкой.

В `private:` сначала идут неизменяемые поля, заданные в конструкторе: настройки
и зависимости. Затем — изменяемое состояние, сгруппированное по ответственности,
например чтение, запись и статистика.

### Конструкторы

Для конструктора с одним аргументом используйте `explicit`, если не требуется
намеренное неявное преобразование. Не добавляйте `explicit` механически:
он влияет и на copy-list-initialization. Конструкторы результата, принимающие
значение или ошибку для удобного `return`, могут намеренно быть неявными.

Параметр, сохраняемый в поле, принимайте по значению и перемещайте:

```cpp
explicit TFile(std::string name)
    : Name_(std::move(name))
{ }
```

Поля, заданные один раз и не меняющиеся после конструктора, объявляйте `const`
и задавайте в списке инициализации. Все примитивные поля явно инициализируются
в объявлении или конструкторе. Не дублируйте инициализацию, если конструктор
по умолчанию уже задаёт нужное состояние.

Для структур с несколькими полями предпочитайте designated initializers:

```cpp
TOptions options{
    .Timeout = std::chrono::seconds(5),
    .Retries = 3,
};
```

### Виртуальные методы

Интерфейсы объявляются как `struct` с префиксом `I`, без явного `public:`.
Операции интерфейса — чисто виртуальные. Допустимы невиртуальные помощники,
выраженные через эти операции, и виртуальный деструктор с `= default`.

В переопределённых методах с `override` или `final` не указывайте `virtual`.
Владение через базовый интерфейс требует корректного виртуального деструктора.

## Фигурные скобки и переносы

Открывающая скобка функции, метода, класса или структуры находится на новой
строке. У класса с наследованием — после списка базовых классов:

```cpp
class TLocalFs
    : public ILocalFs
    , public IStatistics
{
public:
    void Process();
};

void Process(
    const TOptions& options,
    TOutput* output)
{
    WriteOutput(options, output);
}
```

У `if`, `for` и `while` с однострочным условием скобка остаётся на той же строке.
Фигурные скобки обязательны даже для одного выражения.

```cpp
if (condition) {
    Process();
} else {
    Finish();
}
```

У многострочного условия скобка переносится на отдельную строку, а `&&` и `||`
остаются в конце предыдущей:

```cpp
if (condition &&
    otherCondition)
{
    Process();
}
```

Не добавляйте круглые скобки, не помогающие пониманию. Открывающая круглая скобка
остаётся на строке вызова, закрывающая — на строке последнего аргумента.
Закрывающую скобку и точку с запятой отдельно не переносите.

### Тернарный оператор и switch

Если выражение помещается в строку, оставляйте его в одной строке. Иначе:

```cpp
auto answer = condition
    ? someValue
    : otherValue;
```

Открывающие скобки `switch` и `case` остаются на той же строке. Метки `case`
имеют дополнительный отступ. Для `case` скобки нужны, когда внутри больше
одной строки, не считая `break` и `return`.

```cpp
switch (state) {
    case EState::Open: {
        WriteData();
        FlushData();
        break;
    }
    case EState::Closed:
        return GetResult();
    case EState::Failed:
        ReportFailure();
        break;
}
```

### Пустые тела и многострочные вызовы

Пустое тело находится на отдельной строке с пробелом между скобками:

```cpp
struct TEmpty
{ };

void DoNothing()
{ }
```

В перенесённом вызове каждый аргумент находится на отдельной строке с одним
дополнительным отступом. Первый аргумент с форматом сообщения по возможности
остаётся на строке вызова:

```cpp
auto message = std::format("File {} has {} bytes",
    fileName,
    fileSize);
```

В многострочном списке инициализации после последнего элемента ставьте запятую.
В цепочке вызовов каждый уровень продолжения получает один дополнительный
отступ. Явную операцию извлечения результата с исключением переносите на
отдельную строку, если такой интерфейс предусмотрен используемой библиотекой;
это не основание добавлять throwing API в ядро.

## Типы и значения

### Стандартная библиотека и владение

Используйте `std::string`, `std::vector`, `std::optional`, `std::map` и
`std::unordered_map`, выбирая контейнер по нужным свойствам. Специализированный
контейнер требует измеримой причины и отдельного решения о зависимости.

Для единственного владельца используйте `std::unique_ptr`, для действительно
совместного владения — `std::shared_ptr`, для наблюдения без удержания —
`std::weak_ptr`. Сырые указатели и ссылки не передают владение. Не вводите
собственный подсчёт ссылок ради соответствия стилю.

### auto, const и приведения

Для локальных переменных предпочитайте `auto`, для указателей — `auto*`,
особенно когда тип очевиден из фабрики или приведения. Для примитивных типов
явное имя (`bool`, `int`, `double`) часто понятнее. Указывайте сложный тип явно,
если он помогает чтению.

Используйте `const` для неизменяемых значений и `const&`, если копия не нужна.
В циклах предпочитайте `const auto&`, когда не нужны изменение или копирование.
Для изменяемого выходного аргумента собственного API используйте указатель
вместо неконстантной ссылки; обозначьте, допустим ли `nullptr`. Сигнатуры
операторов и внешних интерфейсов сохраняйте. Ссылки и указатели примыкают к типу:
`const TOptions&`, `TOutput*`.

Не используйте C-style casts. Применяйте `static_cast`, `dynamic_cast`,
`std::dynamic_pointer_cast` или другое явное преобразование по его назначению.

Не используйте `std::optional<T*>`, если `nullptr` уже означает отсутствие.
Для идентификаторов и значений используйте `optional`, когда отсутствие —
самостоятельное состояние. Не заменяйте его нулём или пустым UUID без основания
в контракте; в частности, отсутствие snapshot не равно произвольному snapshot.
Используйте `value_or(defaultValue)` вместо повторения проверки optional.

### Контейнеры

Для ожидаемого отсутствия ключа используйте `find` или `contains` и верните
соответствующий результат. Не используйте `operator[]` для чтения с неявным
созданием записи. `.at()` допустим после проверки наличия ключа или при явной
обработке его исключения; lookup не должен превращать повреждение данных
в падение процесса.

Для одного уже созданного значения предпочитайте `insert`, `push` или
`push_back` соответствующему `emplace`. Для map-контейнеров предпочтительны
`emplace(key, value)` и `try_emplace`, когда нужна вставка по ключу без
перезаписи существующего значения.

### Числа и единицы измерения

Для обычных количеств и индексов предпочитайте знаковые типы: `int`,
`std::int64_t`, `std::ptrdiff_t`. Используйте `std::ssize(container)` вместо
ручного приведения размера к знаковому типу.

На границах STL и `std::span` сохраняйте требуемый `std::size_t`. Для битовых
масок, сериализации и явно беззнаковых полей контракта используйте фиксированные
типы, например `std::uint64_t`. Проверяйте переполнение и сужающие преобразования;
не меняйте формат offsets, receipts или budgets ради косметического единообразия.

В крупных десятичных литералах от `10'000`, кратных степени десяти, используйте
разделитель `'`, группируя цифры по три справа: `1'000'000`. Не разбивайте литерал,
если группировка противоречит смыслу значения.

Обозначайте единицы явно, без отдельного фреймворка литералов:

```cpp
constexpr std::int64_t KiB = 1024;
constexpr std::int64_t MiB = 1024 * KiB;
constexpr std::int64_t DefaultBlockSize = 4 * MiB;
constexpr std::int64_t SmallBufferSize = 512 * KiB;
```

Для времени используйте `std::chrono`, если контракт не требует фиксированного
целого представления. Для timestamp на границах формата сохраняйте заданные
единицу, диапазон и точность.

### Современный C++

Предпочитайте языковые средства макросам: `std::memory_order::relaxed`,
`[[likely]]`, `[[unlikely]]`, `[[maybe_unused]]`. Не добавляйте подсказки ветвления
без причины, относящейся к реальному профилю исполнения.

## Шаблоны и inline-определения

Параметры шаблонов объявляйте через `typename`:

```cpp
template <typename T>
void Process(T value);
```

Нешаблонные определения размещаются в `.cpp`, шаблонные и `inline`-определения —
в соответствующем `-inl.h`. В `.h` остаются объявления; `= default` разрешён.
Приватные файлы компонента находятся рядом в `core/`. Если `-inl.h` нужен
публичному заголовку, он тоже должен попадать в установленный пакет и не включать
приватные части ядра.

`-inl.h` подключается только соответствующим `.h`, в самом конце после объявлений.
Для защиты от прямого включения достаточно локального макроса, не требующего
никаких библиотек:

```cpp
#define GLAMDB_CORE_IO_RESULT_INL_H_
#include "result-inl.h"
#undef GLAMDB_CORE_IO_RESULT_INL_H_
```

В начале `-inl.h`:

```cpp
#ifndef GLAMDB_CORE_IO_RESULT_INL_H_
#error "Include result.h instead of result-inl.h"
#endif
```

В `-inl.h` нет `#pragma once` и повторного `#undef`: макросом управляет `.h`.
Имя макроса включает `GLAMDB`, путь компонента и имя файла в верхнем регистре
с заменой разделителей на `_`. После защиты идут дополнительные инклюды,
неймспейс и определения. Макросы генерации smart pointers или подсчёта ссылок
для этого не нужны.

## Перечисления

Все перечисления — `enum class`. Для небольшого внутреннего перечисления
указывайте подходящий underlying type; для сериализуемого — строго заданный
контрактом тип и значения.

Преобразование enum в строку и обратно реализуйте обычной функцией с явной
обработкой неизвестного значения. Не вводите макросный генератор перечислений
или зависимость только ради логирования.

## Лямбды, перемещение и время жизни

Исходный стиль отделяет захваты от параметров пробелом, однако clang-format 18
не поддерживает эту настройку. Для воспроизводимого форматирования в GlamDB
используйте `[](...)`. У лямбды без аргументов скобки можно опустить:

```cpp
[](TValue value) {
    Process(value);
};

[] {
    Finish();
};
```

Для синхронной лямбды, которая никуда не сохраняется, используйте `[&]`.
В лямбде метода захватывайте `this` и обращайтесь к полям напрямую, только
если время жизни объекта гарантировано.

Если callback должен удерживать объект, используйте явный захват сильного
`std::shared_ptr`, например `[this_ = shared_from_this()]`. Если удержание
не требуется, захватите `std::weak_ptr` и проверьте `lock()` при исполнении.
Не вызывайте `shared_from_this()` до появления владельца и не создавайте циклы
владения между объектом и сохранённым callback.

Для перемещения значения из захвата по значению нужна `mutable`-лямбда.
Если поле после перемещения должно оказаться в определённом пустом состоянии,
используйте `std::exchange(Field_, {})`.

## Многопоточность и асинхронный код

Первоначальное ядро синхронно; этот раздел не требует добавлять executor,
очередь или асинхронное API.

Контракт поточности фиксируйте в интерфейсе или краткой документации компонента
и проверяйте тестами. Явно отделяйте методы, доступные из любого потока, от
операций под writer lock. Не вводите макросы thread affinity без поддерживающего
механизма проверки.

Собственная функция с контрактом возврата future возвращает его без скрытого
ожидания; ошибки операции передаются через результат future. Не теряйте ошибки,
игнорируя возвращённый future или callback. Завершение операции и публикация
должны иметь явного владельца.

Не прячьте ожидание commit или финализацию данных в деструктор. Предусматривайте
явные `Close` или `Shutdown`, если вызывающий должен получить ошибку завершения.
Деструктор не бросает исключений и не объявляет незавершённую запись успешной.

## Логирование

Используйте существующий logger компонента; стиль не требует вводить новую
библиотеку логирования. Отделяйте постоянный текст события от структурированных
полей с идентификаторами и значениями. Сохраняйте имена полей установленного
формата трассы или API.

Сообщение должно описывать событие: `File closed`, а не `CloseFile() invoked`.
Текст краткий и естественный, без точки в конце; части при необходимости
разделяются точкой с запятой. Идентификаторы, пути, размеры и коды ошибок
передавайте отдельными полями, когда logger это поддерживает.

Для частых штатных событий используйте `DEBUG`, для редких эксплуатационно
значимых — `INFO`. Ошибки и нарушения инвариантов должны различаться по смыслу;
не выдавайте штатный отказ проверки пользовательского ввода за внутреннюю аварию.

## Ошибки и проверки

Для низкоуровневого I/O используйте `std::error_code` и `TResult<T>` из
[result.h](../../core/io/result.h). На границе зависимости сохраняйте её
публичные status/result-типы и преобразуйте ошибки явно. Не создавайте второй
набор error-макросов ради соответствия стилю.

Проверяйте результат до извлечения значения. Не заменяйте ошибку валидации,
отсутствующий файл, исчерпание памяти или места, повреждение данных и отказ
синхронизации на `assert`, `abort` или безусловное извлечение результата.
Assertions допустимы только для внутренних инвариантов, не зависящих от
пользовательского ввода и внешнего состояния; они не заменяют рабочую проверку.

Сохраняйте исходную ошибку, её код и необходимый контекст. Исключения внешних
библиотек обрабатывайте на границе адаптера; не допускайте их выхода из
деструктора и не преобразуйте их в фиктивный успех. Для записи сохраняйте
различие `Committed`, `DefinitelyNotCommitted` и `CommitUnknown`.

Пользовательские ошибки формулируйте цельными предложениями с естественной
пунктуацией. Не используйте английские сокращения вроде `doesn't`.
Из текста должно быть ясно, что произошло, даже если пользователь не читает
дополнительные атрибуты: `File data.parquet is missing.`
Перегружающие текст подробности выносите в структурированный контекст.

## Аргументы функций

Для неочевидных позиционных значений (`nullptr`, `{}`, булевых и числовых
литералов), а также повторяющихся аргументов одного типа указывайте имя параметра:

```cpp
Process(/*retryCount*/ 0, /*allowPartial*/ false);
```

Такие подписи — структурная документация. Не размечайте очевидные аргументы;
при большом количестве параметров предпочтительнее небольшой объект настроек
с именованными полями.

У неиспользуемого параметра в определении закомментируйте имя без пробелов
внутри комментария или используйте `[[maybe_unused]]`:

```cpp
void Process(int /*unusedCount*/)
{ }

template <typename T>
void Process([[maybe_unused]] T value)
{
    if constexpr (std::is_same_v<T, int>) {
        ProcessInteger(value);
    }
}
```

В прототипах и типах функций имена параметров не комментируйте: они не вызывают
предупреждения о неиспользуемых аргументах.

## Комментарии и документация API

Оставляйте комментарии только для сложной причины или ограничения, которые
не видны из кода, имени теста или сообщения проверки. После изменения удаляйте
пересказ очевидного кода. Количество комментариев рядом не является ориентиром.

Комментарий должен объяснять код, а не отвечать на реплику из ревью.
Обсуждение выбора оставляйте в PR. Схему или компактную запись предпочитайте
длинному объяснению.

Полное предложение пишется перед кодом на отдельной строке, с заглавной буквы
и точкой в конце. Если комментарий только называет сущность и не является
предложением, начинайте его со строчной буквы.

Для `TODO`, `COMPAT` и `XXX` указывайте автора: `TODO(username): explanation`.
Для публичной API-документации используйте Doxygen `//!`, если такой стиль уже
принят рядом. Документируйте существенные условия владения, lifetime, потоков
и ошибок; не дублируйте очевидные имена параметров.

## Имена тестов

Имя собственной fixture заканчивается на `Test` и соблюдает префикс типа:
`TLocalFsTest`. Не добавляйте `Test` в начало имени класса или метода.
Названия тестов описывают проверяемое поведение. Служебные имена, которые
генерирует GoogleTest, не переименовываются вручную.
